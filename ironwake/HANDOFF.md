## 1. 当初の依頼と、実際に採った方針

### 依頼（ユーザー原文の要旨）

- Unreal Engine と Blender を連携し、『アーマード・コア6』に匹敵するAAA品質のメカアクションを作る。
- 核となる要素は、クイックブーストによる高速3D移動と、無骨なインダストリアル・デザイン。
- ロードアウトは固定で、アセンブル機能は不要。
- アリーナ・敵・目標・勝敗判定を備えた、プレイ可能な単一ステージを完成させる。
- サブエージェントを並列展開し、各要素ごとに「辛口の批評役が視覚チェック→AAAに見えなければ作業継続」を反復する。
- AC6と並べたブラインド比較で、批評役が心底感嘆するまで続ける。

### 実際の方針と理由（重要な差分）

| 依頼 | 実際 | 理由 |
|---|---|---|
| Unreal Engine で制作 | **Three.js（WebGL2）のブラウザゲーム**として完成させた。UE5向けにはFBX素材・手順書・設計書・インポート用Pythonを `ironwake/ue5/` に用意 | 作業コンテナにUE5もGPUも無い（Linux・CPU 4コア）。UE5での作業はユーザーのゲーミングPC上で行う前提 |
| Blender 連携 | **実施済み**。`pip install bpy==4.2.0` のヘッドレスBlenderで、メカ2機・敵3種・アリーナをPythonスクリプトから生成。テクスチャのベイクにはCycles（CPU）を使用 | — |
| AC6との並列ブラインド比較 | **実画像での比較は不可能**だった | コンテナのネットワーク制限で、AC6のスクリーンショット（Steam等）を取得できなかった。代わりに、出典付きの採点基準 `docs/AC6_BENCHMARK.md` を作り、批評役がAC6の同場面を想起して比較する方式で代替した |
| 完璧になるまで無限ループ | 各要素を **最大3ラウンド＋最終ポリッシュ1回** で打ち切り | 打ち切りの条件は2つ：改善幅0.25未満が2回続いたら停止、利用上限による中断が複数回発生 |
| AC6風デザイン | **完全オリジナル**（名称・機体・ロゴ・勢力名はすべて独自） | 他社IPを避けるため。設定は「ハルヴァルド深層鋳造港・第7埠頭」、自機 RIG-07 IRONWAKE、敵 Grauwerk、ボス CINDERHOUND、オペレーター LEDGER |

## 2. 現状

### 2.1 ゲームの中身

- **起動**：`ironwake/dist/ironwake.html` をダブルクリック（Chrome / Edge 推奨）。遊び方は `ironwake/README_JA.md`（英語版は `README.md`）。
- **作戦の流れ**：
  1. PK-2 PICKET（歩行MT）×5 を撃破（GNAT ドローンが妨害）
  2. リレー発電機×3 を破壊
  3. ライバル機 CINDERHOUND を撃破（フェーズ2あり）→ MISSION COMPLETE
  - AP 0 または制限15分で MISSION FAILED。リザルトは S〜D ランク。
- **移動**：歩行、地上ブースト、クイックブースト（約105m/s・1フレームで最高速に到達）、アサルトブースト（約130m/s）、ジャンプ／ホバー、ENゲージ（回復ディレイあり、枯渇時は長めのディレイ）。数値の一覧は `ue5/GAME_SPEC.md`。
- **武装（固定）**：右腕ライフル（左クリック）、左腕パルスブレード（右クリック）、左肩マルチロックミサイル（Q）、右肩ヘビーキャノン（E）。スタッガー（姿勢崩し）システムあり。
- **演出**：
  - ポストエフェクト：高さフォグ、ボリューメトリック光芒、AO、ブルーム、カラーグレード、SMAA＋サブピクセル処理
  - 灰の降下、手続き生成のVFX（噴射炎・爆発・煙・火花）、HUD、ブリーフィング画面
  - 音：手続き合成のSE・音楽。オペレーター音声はオフラインTTSを加工したもの
- **画質設定**：OPTIONS の GRAPHICS QUALITY（LOW / MEDIUM / HIGH）、または URL 末尾に `?quality=low` 等。

### 2.2 品質スコアの推移

辛口批評エージェントの採点（10点満点）です。R1〜R3は各要素の制作→批評→修正のラウンドを表します。

| ワールド（アリーナ＋ライティング） | 5.0 | 6.3 | **6.4** | 15% |

- R3の後に「最終ポリッシュ」として全9役割が修正を入れました。例：自機の目の発光、アリーナ外周の地形、VFXの噴射炎、HUDの照準情報の配置、遠景のちらつき抑制、敵の輪郭線。**このポリッシュ後の状態は、批評役による採点を受けていません。**

## 4. 未解決の課題（優先度順）

### 4.1 リリース前に推奨

1. **QA第2ラウンドを実行**し、第1ラウンドの修正を独立に再検証する。プロンプトは `docs/handoff/critic_loop_playbook.md` §6。
2. **縦長・極小ウィンドウでのHUD縮小**（QA B、未修正）。
3. **HUDが自機の足元を隠す**。AP／ENバーが自機のすね付近に重なり、QBの圧力リングや足元の砂煙が見えない。HUD担当と移動担当のどちらで直すか判断が必要。
4. **ブレード撃破時に敵が白飛びする**。`src/enemies/models.js` の `HIT_PULSE`（gain 2.2、coreGain 3.5）が原因。批評役は1.5程度への抑制を推奨しています。

### 4.2 見た目の品質（批評役・各担当が挙げた主な残課題）

- **メカ**
  - 摩耗や汚しがゲーム中の距離では弱い。
  - テクセル密度が約90px/m で、ステンシル文字がぼやける。
  - 大きな装甲板の情報量が不足。
  - 足が箱型のまま。
  - ボスは自機より作り込みが劣る。
- **ワールド**
  - 遠景のラチス（格子構造）がざらつく。遠距離用の簡略版が必要。
  - TAA（時間方向のアンチエイリアス）が無いため、動くと細部がちらつく。
  - 太陽側は白っぽく抜け、嵐側は暗すぎる。
  - 地面の照り返しがちらつく。
- **戦闘フィール**
  - 地上ブーストの噴射炎の量感が不足。
  - アサルトブーストを後方から見ると炎が円盤に見える。
  - 正面からのQBで炎が隠れる。
  - ミサイル軌跡の先頭がクリーム色になる。
  - 爆発の後半が地面上のドーム状に見える。
- **敵**
  - 74〜109m先のMTは画面上25〜40px程度で、照準枠に埋もれる。
  - 乱数シードによってボス戦の難度のばらつきが大きい。
  - MTが遮蔽物を使わない（cover plans = 0）。
- **HUD・音**
  - 照準情報の箱がまだ重い。
  - 数字専用フォントのため、英字が別書体になる。
  - オペレーター音声はTTSを加工したもので、ロボット的に聞こえる可能性がある（本当の解決は人の声の録音）。
  - 音全般を誰も耳で確認していない。

### 4.3 予算・技術的負債

- ドローコール 567／600、ポリゴン 267万／300万。敵の輪郭線（outline）がMT1体あたり約2.5万、ボスは約7.8万ポリゴンを消費。
- 単一ファイル 12.1MB（警告ライン14MB、ビルドは15.5MBを超えると失敗する）。
- ヘッドレス撮影は CPU 負荷が高いとタイムアウトしやすい。リトライ機能は実装済みです。

### 4.4 Unreal Engine 5 への移植（未検証）

- 置き場所：`ironwake/ue5/`（39.8MB）。すべての文書の冒頭に「UE5で未検証」と明記してあります。
- 中身：
  - `README_JA.md`：非プログラマー向けの導入手順
  - `CLAUDE.md`：UE5プロジェクトの設計書
  - `GAME_SPEC.md`：実際のゲームから抽出した数値表
  - `PROMPTS_JA.md`：Claude Code ＋ VibeUE 等に貼るための段階的な指示文
  - `import_ironwake.py`：Unreal Editor 用の Python インポートスクリプト
  - `assets/`：自機・ボス・敵3種・アリーナの FBX ＋テクスチャ（T_*_BC/_N/_ORM/_E）
- 初回実行時に修正が要る可能性がある箇所：
  - 軸の向き：アリーナが鏡像になったら、`import_ironwake.py` の `AXIS_MIRROR_Y` を切り替える。
  - 新しいInterchange取り込み方式がFBXの取り込みオプションを無視する可能性。
  - アリーナ部品の一部にUVが無く、ライトマップ関連の警告が出得る。
- 素材の再生成：`npm run ue5:arena` と `npm run ue5:package` が使えます。各メカ・敵のFBXは `blender/` の各ビルドスクリプトで生成し直せます。

## 5. 次に実施すべきこと（推奨手順）

1. **環境を準備する**（§7）。最初に `npm run check` と `npm run smoke` が合格することを確認する。
2. **QA第2ラウンド**（playbook §6）→ 見つかった S／A を修正 → 再検証。修正が同じ箇所で2回失敗したら、場当たり修正をやめて根本原因から設計し直すこと。
3. **最終ブラインド審査**（playbook §7）：
   1. 撮影担当が中立的なファイル名（img_01…）で画像を用意する。
   2. 対応表は別フォルダ（例：`/tmp/claude-0/blind/key/`）に保存し、審査員には見せない。
   3. 審査員は3つの視点（アート／ゲームフィール／画質技術）で、作者を伏せた状態で評価する。
4. 時間と予算があれば、§4.1〜4.2 の課題に批評ループを追加で回す。手順は playbook §2〜4（担当別の指示文、批評役の指示文と出力スキーマ）。
5. 変更後は毎回 `npm run build` で `dist/ironwake.html` を作り直し、一緒にコミットする（配布物は追跡対象）。
6. UE5移植は、ユーザーのゲーミングPC上の Claude Code（＋ VibeUE などの Unreal 用 MCP プラグイン）で、`ue5/README_JA.md` と `ue5/PROMPTS_JA.md` に沿って進める。

## 7. 開発環境の再現手順

これまでの作業環境：Linux、CPU 4コア、GPUなし。

- **Node.js 22**：`cd ironwake && npm ci`。three@0.186.1、esbuild、playwright@1.56 が入る。
  - Playwright の Chromium はヘッドレスで SwiftShader を使い、WebGL2 を CPU で描画する。起動引数は `--use-angle=swiftshader --enable-unsafe-swiftshader --ignore-gpu-blocklist`（`tools/shoot.mjs` と `tools/smoke.mjs` に組み込み済み）。
  - Chromium が無い環境では `npx playwright install chromium`。
- **Python 3.11**：
  - `pip install bpy==4.2.0`：Blender本体はPython版。Cycles の CPU ベイクに使う。EEVEE は GPU が無いため不可。
  - `pip install pillow numpy scipy matplotlib soundfile lameenc pyworld espeakng-loader`：後ろの4つは音声とVOの生成用で、ゲーム実行には不要。
  - gltfpack（GLB の meshopt 圧縮）：`cd ironwake/blender/tools && npm install`。
- **主なコマンド**（`ironwake/` で実行）：

| コマンド | 役割 |
|---|---|
| `npm run check` | バンドル検査、マニフェスト検査、`Math.random` 禁止チェック、ユニットテスト |
| `npm run smoke` / `npm run smoke -- --dist` | 自動プレイテスト（開発版／配布版）。約5〜6分 |
| `npm run shoot -- --shot gameplay_chase --w 1600 --h 900 --out <dir>` | 撮影用シーンを PNG 出力。`--all`、`--frames`、`--contact`、`--cam x,y,z --look x,y,z --fov 50` も使える |
| `npm run telemetry` | 移動の速度・EN・FOV の時系列グラフ |
| `node tools/ai_log.mjs` | ボス戦AIのログとグラフ |
| `node tools/audio_sheet.mjs` | 全SEの波形とスペクトログラム |
| `npm run build` | `dist/ironwake.html` を生成 |
| `npm run serve` | 開発サーバー（ランダムポート） |

- **URL パラメータ**：
  - `?test=1`：TEST API を有効化（`window.__iw`）
  - `&shot=名前`：撮影用シーンを再生
  - `&quality=low|medium|high`
  - `&debug=1`：FPS などを表示
  - `&skip=1`：メニューを飛ばして出撃
  - `&seed=N`
  - `&asset.<id>=<url>`：アセットの差し替え

## 8. 守るべき作業ルール（これまでの契約）

- **役割ごとのファイル所有**（`docs/ARCHITECTURE.md` §2）を守る。他担当のファイルは最小限のAPIレベルの変更にとどめる。`src/manifest.js`、`src/scenes/shots.js`、`src/main.js` の `SYSTEM_MODULES` は追記のみ。
- **決定性**：`src/` で `Math.random()` や `Date.now()` を使わない。乱数は `game.rng.stream('名前')` を使う（check で強制される）。
- **予算**：ドローコール600以下、ポリゴン300万以下、毎フレームの new 禁止（プールとスクラッチを使う）、ライト数は固定、リスタート時に dispose する、単一ファイルは15.5MB以下。
- **作業完了の条件**：`npm run check` と `npm run smoke` が合格し、コンソールエラーが0件であること。見た目を変えたら必ず `npm run shoot` で撮影し、画像を目で確認する。
- **リリース**：`npm run build` で作った `dist/ironwake.html` をソースと同じコミットに含める。
- **オリジナルIPのみ**：AC6／フロム・ソフトウェア／バンダイナムコの固有名・ロゴ・機体意匠は使わない。AP、EN、クイックブーストなどのジャンル用語は可。
- **ライセンス関係**：
  - three.js、esbuild、gltfpack は MIT。
  - フォントは @fontsource 経由の OFL（Barlow Condensed、Share Tech Mono、Noto Sans JP のサブセット）。
  - 次の2つは開発時の道具として使っただけで、配布物には含めていない：bpy（Blender、GPL）、espeak-ng（GPL、VO 生成用）。
  - VO 音声はこれらで生成した出力ファイルのみを同梱している。気になる場合は専門家に確認すること。

## 9. 既知の落とし穴

- ヘッドレス撮影（SwiftShader）は遅く、他の重い処理（Blender のベイク等）と同時に走ると `page.screenshot` がタイムアウトしやすい。リトライ機能はあるが、単独で実行するのが確実。
- ヘッドレス環境では MSAA と実際のポインターロック挙動を再現できない。マウス操作の検証は TEST API と、ロックを拒否したときのフォールバック試験で代替している。
- 実GPUでの性能は一度も計測されていない（§3.3）。
- 単一ファイル版は `DecompressionStream`（最新の Chrome / Edge / Firefox / Safari）が必要。非対応ブラウザには日英の案内画面が出る。
- 作業コンテナの再起動で、バックグラウンドの作業が何度か失われた。こまめにコミット・プッシュすること。
